## 3. 对话形成的产品与开发约定

以下内容是项目所有者与 Codex 的连续对话中反复确认的决定。新增功能应继续遵守。

### 3.1 玩家文档与发布

- `docs` 中每款游戏只保留一份主文档，合并游戏介绍、完整玩法、设置、操作、管理员命令和文末验收记录。
- 根 README 只保留安装前提、建桌／删桌、最小桌距、权限、常用 Debug 与中止模板、游戏索引。
- 资源包 README 内容较短，链接数据包、下载页、兼容性与资源署名。
- 玩家规则和设置界面文字以当前实现为准，不能让旧生成器、旧分支或旧文档覆盖新规则。
- 网站版 23 款规则由 `tools/export_website_game_rules.py` 导出到桌面发布目录，包含游戏图标、现有流程图和截图占位清单。
- 发布 ZIP 只放游戏运行所需的 `data/` 或 `assets/`、`pack.mcmeta`、`pack.png`、README 等白名单文件；不打包 `tools/`、`docs/`、`.source/`、测试世界和临时文件。
- 正式发布页、更新日志和期刊口稿位于桌面发布目录，已有 v1.0 与 v1.1 文稿。

### 3.2 兼容性与版本

- 当前主线目标是 Minecraft Java 26.2。
- Fabric 与钠由项目所有者实测兼容。
- Forge 与 OptiFine 尚未由项目所有者确认；README 目前写“应该兼容”，对外表达时不要升级成“已实测”。
- 资源包版本分支会移除 `assets/minecraft/sounds/` 与 `assets/minecraft/sounds.json`，避免发布包覆盖原版唱片音频。
- `main` 保持 26.2 开发状态；版本适配放在对应发布分支，不在 `main` 混入旧格式修补。

### 3.3 牌桌公共行为

- 四座桌容量 4，八座桌容量 8；椅子数量可在游戏设置中调整，入口位于牌桌皮肤下方。
- 默认启用满桌椅子，不能少于当前游戏最低人数或已入座人数。
- 八座桌同一侧只剩一把椅子时，该椅子居中。
- 实际座号不压缩，所有游戏必须支持稀疏座位。
- 任一本局参与者离线后整桌暂停，等待原参与者全部上线；不设超时自动结束。
- 暂停期间仍允许结束投票和管理员中止，规则输入、计时、人机、发牌与动画推进冻结。
- 游戏已经结束后，离线玩家再上线时必须清除上局道具、HUD、身份、标签和临时分数，不能自动加入新局。
- 游戏中下马不等于退出参与身份；重新右键原座可坐回。
- 每款游戏都提供 `/function <namespace>:admin/abort`，只中止同维度 8 格内最近一桌对应游戏。

### 3.4 UI、设置与操作

- 游戏规则窗口使用统一对话框格式，介绍人数、目标、操作、流程、特殊规则、暂停和管理员命令。
- 游戏设置以单页对话框加可点击文本组件为主，点击后立即生效；完成按钮只关闭窗口。
- 原版 `number_range` 没有拖动回调，需要滑块时保留同页确认，不虚称即时保存。
- 普通玩家默认不需要 OP。谍报风云、问非所答、命悬一线使用文字对话框提交时存在 OP 限制，默认书模式不需要。
- 对话框中的玩家名必须先解析成静态文本组件，不能直接把选择器字符串显示给玩家。
- Q 指 Minecraft“丢弃物品”键。游戏道具应只在玩家有待完成操作时发放，Q 后立即返还或在状态变化时回收。
- 过期窗口、跨桌提交、错误回合、错误座位、重载前 nonce 均须拒绝；一次性输入成功后消费 nonce。
- 私有手牌优先使用 BetterTitle；桌面展示、HUD、物品和动画都只是规则状态的视图。

### 3.5 动画、声音与模型

- 随机结果先由规则层锁定，再播放动画；动画不能重新抽牌、重投骰或二次扣费。
- 发牌和摸牌复用公共发牌动画；胜者烟花复用内置 SK Firework。
- 棋子移动、吃子、建造、交易、投骰等尽量带动画、粒子和音效。
- 背景音乐是可关闭设置，只向本桌玩家播放；暂停、离桌、结束和重载时要停止旧播放。
- 模型、纹理、物品定义、字体和声音事件要同时更新，并在 `.source` 保存可编辑源与素材许可。
- 密集棋盘不要为每个空格建立交互实体。五子棋、围棋使用射线与棋盘平面定位；卡坦岛使用地块、顶点、边拓扑。

### 3.6 各新游戏的关键决定

- **UNO（11）**：手牌用 BetterTitle；出牌选择与斗地主相同，亮框单选；牌名使用 `r7`、`bskip` 等语义名；仅本人回合发手牌道具；牌盒常驻桌心；发牌和摸牌有动画；胜者位置放 SK Firework。
- **国际象棋（12）**：始终白先；按座位选边为默认，随机模式自动换座且不能重座；选中棋子后显示合法格；计时、悔棋、和棋、认输合并到最后一格菜单；结束后保留终局棋面；被吃棋子放在吃子者右侧；单人三档人机。
- **中国象棋（13）**：默认按座位分红黑；单人三档人机；保留标准象棋与揭棋。揭棋中将帅明置，其他子盖放；暗子首次按所在位置的棋种走，翻开后按真实身份走，明士象可过河。
- **五子棋（14）**：13×13、15×15、19×19；无禁手；只保留经典与木色棋盘；三档人机；优化目标是减少上百个交互实体。
- **飞行棋（15）**：只保留一套棋盘；可设置是否开启电脑补位；仅己方回合发骰子；骰子有动画，手持模型缩小。
- **阿瓦隆（16）**：5～8 人，仅八人桌；由同伴持续维护，已提供管理员中止入口。
- **情书（17）**：21 张版；编号固定 17；字体缺字曾修复；最新加入直接手牌物品和第三人称牌背保密。

- **围棋（20）**：13×13、15×15、19×19；复用五子棋棋盘棋子；黑先、面积计分、默认贴目 7.5；基础人机、占地估算、死子确认、停一手、悔棋、认输、计时和复盘。

## 5. 数据包架构

### 5.1 根目录

```text
fimel_cards/
├─ data/                    运行时数据包内容
├─ docs/                    每款游戏唯一主文档、架构规范与验收
├─ tools/                   生成、注册、审计、资源检查和原版测试
├─ pack.mcmeta              26.2，格式 107
├─ pack.png
└─ README.md                玩家入口
```

`data/minecraft/tags/function/load.json` 依次加载合并库、牌桌核心和 23 款游戏。`tick.json` 先执行 `cardtable:session/pre_tick`，再执行公共调度／动画库、`cardtable:tick` 和各游戏 tick。不要把游戏 tick 放到会话预检查之前。

### 5.2 公共牌桌 `cardtable`

`cardtable` 负责：

- 创建、注册和删除四座／八座桌。
- 控制器、座椅、实际座号和椅子布局。
- 大厅菜单、游戏选择、设置入口、规则入口和开始分派。
- 通用结束投票、断线暂停、重连与旧局清理。
- 公共发牌、飞牌、文字和桌面动画。
- 游戏 ID 与命名空间分派。

每张桌有一个 `minecraft:marker`，带 `ct.controller`。关键记分项：

| 记分项 | 含义 |
| --- | --- |
| `ct_id` | 全服唯一桌号 |
| `ct_state` | 0 大厅，1 游戏中 |
| `ct_game` | 游戏编号 |
| `ct_capacity` | 桌型容量 4 或 8 |
| `ct_chairs` | 当前启用椅子数 |
| `ct_c1`～`ct_c8` | 各实际座号是否启用 |
| `ct_session` | 当前局唯一会话号 |
| `ct_expected` | 开局冻结的真人数 |
| `ct_paused` | 缺员暂停标记 |
| `ct_start` | 游戏成功开局握手 |
| `ct_votes` | 有效结束票数 |

参与者带 `ct.player`，并保存同一 `ct_id` 与实际 `ct_seat`。实例归属必须以桌号比较，距离只用于缩小候选范围。

### 5.3 每款游戏的标准职责

建议目录：

```text
data/<namespace>/function/
├─ load.mcfunction
├─ tick.mcfunction
├─ game/       init_table、start、finish、abort、end_vote、remove
├─ player/     clear_state、重连恢复
├─ settings/   设置页、校验、默认值
├─ rules/      游戏内规则窗口
├─ input/      Q、右键、trigger、掉落物入口
├─ ui/         对话框与按钮
├─ visual/     桌面模型与 HUD
├─ sound/      每桌声音和音乐
├─ system/     install、upgrade、reload
└─ debug/      状态检查
```

必须实现或接入的生命周期接口：

- `game/init_table`：幂等补设置，不重置活跃对局。
- `game/start`：校验人数、快捷栏和设置；完成后置 `ct_start=1`。
- `game/finish`：锁定结算并防止重复进入。
- `game/end_vote`：通用层通过票数后调用。
- `game/abort`：任意阶段安全中止并完整清理。
- `admin/abort`：玩家在 8 格内定位最近一场对应游戏。
- `player/clear_state`：只清本游戏状态，不误删普通物品或邻桌状态。
- `settings/open`、`rules/show`：由公共层标记接收者后调用。

### 5.4 注册点

新增或删除游戏时，必须同步：

- `cardtable:load` 的游戏数量。
- 四座／八座选游菜单、按钮提交值和人数说明。
- `menu/select_game`、`menu/render`、`menu/game_name_<namespace>`。
- `game/init_selected`、`game/start`、`game/open_settings`、`game/open_rules`。
- `vote/finish`、`table/remove`、离线玩家清理和重连恢复分派。
- `minecraft` 的 load／tick 标签。
- 根 README、`docs/README.md`、`tools/game_rules.json`、游戏图标和发布文档。
- `tools/build_table_chair_settings.py` 的最低人数。
- `tools/build_table_sessions.py` 与 `tools/build_table_pause_guards.py` 的会话／暂停注册。

优先修改对应 `register_*.py` 与结构化源，再运行生成器；不要只手改分派产物。

### 5.5 规则状态、保密与交互

- 控制器、专属 marker 或游戏 storage 保存权威状态。
- HUD、对话框、桌面模型、快捷栏和动画只显示已授权的信息。
- 私有手牌、身份、暗子、交易库存不能通过旁观实体、失败提示或人机模拟泄露。
- 所有输入复核桌号、会话、实际座号、阶段、回合、窗口 nonce、加载代号和局面 epoch。
- 多项支付、退还、交易、目标选择在确认时原子提交，不能点击一项就永久扣一项。
- 交易接受时再同时复核双方库存；失败不能成为探测对手私有资源的渠道。

### 5.6 设置和规则的权威来源

- 游戏内规则正文：`tools/game_rules.json`。
- 规则窗口生成：`tools/build_game_rules.py`。
- 早期游戏统一设置：`tools/build_legacy_settings.py`。
- 公共椅子数量：`tools/build_table_chair_settings.py` 和 `tools/table_chair_settings.py`。
- 公共断线暂停：`tools/build_table_sessions.py`、`tools/build_table_pause_guards.py`。
- 每款游戏详细玩家文档：`docs/<游戏>.md`。
- 网站规则导出：`tools/export_website_game_rules.py`。

生成器必须幂等。若手改生成产物而不同步模板或生成器，下次运行会丢失修改。

### 5.7 合并的前置库

数据包已经内置所需前置，不要求玩家另外安装：

- `fimel_anim_text`：文本动画。
- `fimel_title`：BetterTitle 私有 HUD。
- `fimel_skform`：表单／对话框辅助。
- `fimel_sklibs`：数组、数学、调度、动画和 SK Firework。
- `fimel_math_light`、`fimel_vendor`：其他合并依赖与兼容入口。

上游来源、说明与笔记保存在 `docs/vendor` 和前置合并清单中。不要为了升级单一功能整包覆盖这些命名空间。

### 5.8 动画与性能边界

- 公共发牌入口位于 `cardtable:animation/deal/`。
- 规则结果提交后才入动画队列；重载可以丢表现队列，但不能重复规则效果。
- 大棋盘通过计算目标点降低实体量；不要为每个空格长期生成 `interaction`。
- 人机和复杂规则搜索要按刻分批，有明确上界和局面 epoch。
- 默认 `max_command_sequence_length=65536` 下运行，不依赖提高全服限制。
- 所有长期实体带游戏标签和 `ct_id`；清理同时校验两者。

## 6. 资源包架构

### 6.1 根目录

```text
fimelcard-rp/
├─ assets/
│  ├─ card/                 大多数牌、棋盘、棋子、道具、GUI、字体和声音
│  ├─ minecraft/            必要的原版命名空间适配；发布分支会移除唱片覆盖
│  ├─ title/                BetterTitle 相关资源
│  ├─ meme/                 表情包
│  ├─ splendor/             璀璨宝石独立字体／声音命名空间
│  └─ magical_athlete/      胡闹运动会独立字体／声音命名空间
├─ .source/                 可编辑模型、源图、生成脚本、许可和素材清单
├─ tools/                   资源审计与辅助脚本
├─ pack.mcmeta              26.2，格式 88
├─ pack.png
└─ README.md
```

### 6.2 资源引用链

常见物品完整链路：

```text
数据包 item_model
  → assets/card/items/<path>.json
  → assets/card/models/item/<path>.json
  → assets/card/textures/item/<path>.png
```

界面大图使用 bitmap font：

```text
assets/<namespace>/font/*.json
  → assets/<namespace>/textures/font/*.png
```

声音链路：

```text
assets/<namespace>/sounds.json
  → assets/<namespace>/sounds/*.ogg
  → 数据包 playsound / stopsound
```

修改模型时同时检查物品定义、模型父级、纹理路径、显示上下文、字体切片和数据包中的 `item_model`。仅有模型 JSON 并不代表物品能够被 26.2 客户端解析。

### 6.3 `.source` 是制作源

当前 `.source` 包含飞行棋、棋类、UNO、花火、掼蛋、情书、卡坦岛、璀璨宝石、胡闹运动会等可编辑源。约定：

- Blockbench 模型保留 `.bbmodel`。
- 程序绘制纹理保留生成脚本和结构化数据。
- 外部音频保留来源 URL、许可、原件或哈希。
- 导出器重复运行应得到相同产物。
- 网站／发布 ZIP 不包含 `.source`，Git 仓库必须保留。

### 6.4 字体与 HUD 限制

- 26.2 单个 bitmap 字形原始切片宽高都不能超过 256 像素。
- `height` 只改变显示比例，不会缩小上传纹理。
- 大牌图应切成多个字形或另做 HUD 小图。
- 叠牌字距、负宽字体、选中框、数量文本和点击区域使用同一几何计算。
- 牌面数字、功能符号和资源图标须在最终显示尺寸下仍能辨认。

### 6.5 声音和音乐

- 每款游戏使用独立声音事件和每桌播放状态。
- `stopsound` 不能误停其他游戏或其他桌。
- 暂停时停止当前流，恢复时为在线和刚重连玩家重新播放。
- 引用 CC0 或其他外部资源时保留许可和来源；不要只留下压缩后的 OGG。

## 7. 生成、审查与测试流程

### 7.1 开始修改前

1. 两个仓库分别 `git fetch`、检查 `git status` 和当前分支。
2. 阅读目标游戏主文档、相关生成器和最近同伴提交。
3. 确认源文件与生成产物的关系，不直接在产物上做唯一修改。
4. 若同伴刚推送，先比较基线和候选提交，避免旧文件覆盖新文件。

### 7.2 修改后

1. 运行目标游戏生成器，确认第二次运行无差异。
2. 若涉及公共椅子、会话、暂停、规则或选游菜单，运行对应公共生成器。
3. 运行资源引用检查、JSON 解析、`git diff --check`。
4. 使用 `tools/audit_git_history.py` 检查历史回退、误删与旧文件复活。
5. 在临时世界运行原版 26.2 测试；不要在玩家实际存档执行破坏性测试。
6. 客户端检查 HUD、字体、点击区域、模型朝向、声音、动画和真人联机。

### 7.3 常用测试类别

- 公共桌：椅子布局、设置入口、断线暂停、重连、结束投票、选游图标。
- 游戏规则：人数边界、稀疏座位、两种桌型、非法输入、过期窗口、重载与两桌隔离。
- 资源：模型／物品／纹理闭包、字体切片、声音事件与音频格式。
- 新直接交互：`tools/test_direct_interactions.py`。
- 游戏内规则：`tools/test_game_rules.py`。
- 选游：`tools/check_game_picker.mjs`、`tools/test_game_picker_icons.py`。

服务端断言通过不等于客户端画面已确认。交接记录中要分别写“自动测试通过”和“客户端待测”。

## 8. Git 与协作约定

- 数据包和资源包分别提交、分别推送，中文 commit 标题说明具体行为。
- 合并前先拉取并阅读同伴差异；产生冲突时按功能逐段合并，不整文件选择旧方或新方。
- 不使用 `git reset --hard`、不批量恢复整个目录解决冲突。
- 对生成产物有冲突时，先合并结构化源和生成器，再重建并审查产物。
- 不删除《命悬一线》、题库、阿瓦隆、揭棋、同伴资源或来源记录。
- 如果旧生成器会覆盖新界面、文档或直接交互，先修生成器调用链，再运行。
- 提交前确保两个仓库工作区只包含本次目标，避免把桌面发布文件、临时测试世界或缓存带入 Git。

## 9. 当前高风险与待复测项

1. **直接交互客户端复测**：卡坦岛右键建造、璀璨宝石点击命中、情书第三人称牌背、胡闹运动会快捷栏流程需要真人客户端完整测试。
2. **生成器跨仓库写入**：`build_direct_interactions.py` 会修改两个资源目录，CI 或其他目录布局下可能写错位置。
3. **直接交互文档漏项**：`docs/直接交互.md` 没有写情书，标题数量也与实际四款游戏不一致。
4. **Forge／OptiFine**：仍是未实测兼容，不要写成已验证。
5. **命悬一线**：README 仍标注开发验证中，发布前应由同伴确认蛛丝、红线、权限与题库完整性。
6. **生成覆盖**：中国象棋揭棋、情书字体、飞行棋骰子尺寸、UNO HUD、卡坦岛引导和胡闹运动会直接交互都曾被旧产物覆盖过，重建后必须审查 Git 差异。
7. **资源包发布分支**：打包前确认没有重新带回原版 `assets/minecraft/sounds/` 和 `sounds.json`。

## 10. 推荐接手顺序

1. 阅读根 README、本交接文档、新游戏接入规范和目标游戏主文档。
2. 阅读目标游戏的 `build_*.py`、结构化配置及最后一次相关提交。
3. 在临时分支或工作树完成修改，先改源再生成。
4. 运行该游戏测试和受影响的公共回归。
5. 启动客户端进行画面、声音、交互和多人验证。
6. 更新唯一主文档、`tools/game_rules.json`、README 和网站规则导出。
7. 数据包与资源包分别中文提交，拉取合并远程后再推送。

出现“游戏功能还在，但规则／设置／资源变旧”的情况时，优先排查生成器和分支覆盖，不要直接在产物上重复补丁。这个项目目前最重要的维护原则是：**控制器状态为规则权威、结构化源为生成权威、每款游戏只有一份主文档、同伴的新功能不得被旧生成流程抹掉。**
